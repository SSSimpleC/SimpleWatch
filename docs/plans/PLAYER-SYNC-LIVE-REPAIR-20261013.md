# SimpleWatch 播放器同步与直播专项修复计划

本计划只解决跨浏览器观看、Host 拖动后的观众同步、直播低帧率及延迟积累。视频和音频均不转码，不增加 HAProxy、Coturn 或其他基础设施。优先恢复可靠同步和连续画面，再优化端到端延迟。

截至 2026-10-23 凌晨，专项代码已通过模块、协议、安全、覆盖率和三浏览器回归，并按用户授权完成本地提交、干净源码重建和仅 App/Worker 的受限发布；未推送、未合并。iPad Edge 和真实 OBS 验收仍待进行，目标未完成。实施记录见 `../gates/PLAYER-REPAIR-20261022.md`。代码审查基线是本地 `origin/main` 的 `47d60363d6c14c4c6da1d4d6413bbaf1d878e72c`，正式应用提交为 `0b69925f59392c2289ccd608693053416482ab06`。本文件的范围覆盖旧计划中与此冲突的转码和新增中继方案。

## 范围约束

1. 不新增视频或音频编码任务；禁止 AAC 转换、声道混缩、重采样等隐藏兜底。
2. 现有必要的纯流复制重封装可以保留，例如容器整理、`faststart` 和合法标记修正，但必须保持选中音视频流的编码内容不变；重封装不能解决解码能力不足。失败时保留输入并明确报错，不尝试转码。
3. OBS 原有的采集编码是现存推流步骤，不在家庭或云端再解码重编码。OBS 设置先原样测试；调整任何参数前记录基线并征得用户同意。
4. 不增加容器、后台进程、消息系统、中继、域名或端口；不调整系统代理、Clash TUN、路由器或安全组。
5. 不改家庭 Agent、Library 扫描、节目队列、缓存淘汰和上传架构，不迁移数据库。Library 中都是完整下载文件，不引入 qBittorrent 临时后缀判断。
6. 不删除、重传、批量加工现有影片；不操作家庭两块 HDD。保持既有账户权限、签名媒体访问和撤权行为。
7. 不承诺所有浏览器播放所有原始编码。不支持的设备应准确提示；不能为了通过验收偷偷转换媒体，或仅换浏览器来宣称原问题已解决。

## 第一阶段 建立最小复现与证据

使用同一部问题影片、Mac Host 和 iPad 独立观众账户，记录一次向前跳转、一次向后跳转及一次暂停跳转。暂不更换编码、媒体地址或服务器配置。

每条控制命令关联 `commandId`、房间、媒体、版本和连接代次，串起六个节点：Host 提交、服务端接受、观众收到快照、请求定位、`seeked` 完成、目标视频帧呈现。按事件顺序及服务器校时关联记录，不直接比较不同设备的本地时钟。

若 iPad 未收到新版本，先修连接恢复和消息交付；若已收到但未开始定位，修调度；若反复定位，修纠偏；若定位完成仍显示旧画面，检查解码与媒体请求。保留网络错误、播放拒绝和实际帧状态，不能仅凭进度条变化判定成功。

诊断优先复用现有页面和本地有界记录，不建设监控平台。Host 若需要查看观众结果，通过现有 WebSocket 增加小型状态消息：通常每 2 秒一次，服务端每席位最多接收每秒一次，整包上限 4KiB，内存保留 30 秒；仅当前授权 Host 可见，不落数据库，不改变观看覆盖或队列判断。身份来自已认证会话，不相信客户端自报身份，不记录令牌、签名 URL 或文件系统路径。

## 第二阶段 修复点播同步和跨浏览器行为

### 控制命令交付

- Host 同时最多一个在途控制命令。仅合并尚未发送且相邻的 seek；不越过播放、暂停或切片操作合并。
- 服务端成功确认包含命令 ID 和权威版本，客户端确认后才发送下一条。重复 ID 使用现有幂等结果，不二次执行、不重播旧全房状态。
- 3 秒没有确认时最多重试一次，沿用原 ID；10 秒仍无法确定结果则结束等待、显示结果未知并拉取权威快照，不能声称命令失败或成功。拒绝后也刷新，不盲目继续旧版本队列。
- 结果未知后立即冻结并废弃尚未发送的队列，界面明确提示未发送操作已取消；取得最新快照后才允许用户重新操作，不自动重放。迟到确认只用于标记原命令结果，不能解冻旧队列。确认中的“原执行版本”与重新获取的“当前房间版本”分开处理，前者不能覆盖后者。
- 切换房间或影片时清理旧上下文；迟到确认不能影响新影片。此次不得顺手更改节目激活和预取重试语义。
- 新增字段保持可选并声明能力，避免已打开的旧页面被突然破坏。旧页面不具备新确认能力时应提示刷新，不能假装具备完整保证。

### 播放器定位

- 同一媒体始终只保留最新定位意图。元数据未就绪时排队，旧请求完成后也不能覆盖新目标。
- 服务端未来生效时间必须真正参与调度；到点以前保持原播放锚点，不能提前跳转。定时器使用单调时钟，重新校时后按最新权威状态协调。
- 明确的 Host seek 优先执行一次；定位中等待事件和新帧，周期任务不能每 500ms 再次改写 `currentTime`。
- 暂停跳转以目标静止帧和暂停状态验收，不要求连续播放；播放跳转需目标画面之后继续推进。
- 初始调参值：150ms 以内不纠偏，150ms 至 2 秒使用相对基础速度最多 ±10% 的短时微调；超过 2 秒且未在定位、缓冲或后台时才允许硬定位，普通硬定位至少间隔 5 秒。明确的新 Host seek 不受普通漂移冷却阻挡。
- 每个定位意图最多一次补偿定位；自最后一次用户目标起 10 秒仍无进展，显示失败与重试入口。定期快照和内部重试不能无限重置计时。
- `requestVideoFrameCallback` 可用时检查 `mediaTime` 和 `presentedFrames`，而非 JavaScript 回调次数。没有该能力时标记证据不足，采用事件和进度辅助诊断并以真机画面补验，不能伪造已呈现证据。[帧回调语义](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

### 浏览器恢复与界面

- 返回前台或网络恢复时，同时获取最新快照和校时。相同版本允许重新协调本机播放器，但不得重复执行已完成命令。
- 心跳超时采用可重连关闭码；认证失效、踢人和关房仍为终止状态，不以自动重试绕过撤权。
- 正确处理鼠标、触控、键盘提交以及 `pointercancel`，避免一次拖动被 pointerup 和 blur 重复提交。
- 捕获 `play()` 拒绝：需要手势时显示可点击恢复按钮；点击必须实际调用播放器恢复，不因“已建立连接”而直接返回。格式错误、网络错误、权限过期分别提示。[播放 Promise 与自动播放限制](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)
- 最小界面调整只包括：Host 的提交和确认状态、观众的同步中或待点击状态、明确错误、一次重试入口和可折叠诊断。不改整体布局，不另建管理后台。
- 保留真实媒体鉴权和 Range 路径；核对跳转时的 206、Content-Range、MIME、签名有效期及拒绝响应。仅修复证据指向的问题，不关闭验证、不全量预下载。

## 第三阶段 修复直播低帧率和延迟积累

### 在同一时段定位瓶颈

| 环节       | 必须观察的内容                                             | 判断限制                                   |
| ---------- | ---------------------------------------------------------- | ------------------------------------------ |
| OBS        | 实际编码输出、渲染和编码跳帧、输出阻塞、当前设置           | 预览帧率和设置帧率不等于实际输出           |
| OBS 到云端 | 当前发布会话的收包、丢包、抖动和码率变化                   | 没有指标是未知，不能当作上行良好           |
| 云端转发   | 对应会话发送量、CPU 节流、内存、网络吞吐与其他现有任务负载 | 仅凭容器 running 或平均 CPU 低不能排除瓶颈 |
| 观众       | 收到、解码、丢弃和呈现帧，短窗口缓冲延迟、选中连接和 RTT   | RTT 和缓冲量不能代替玻璃到玻璃延迟         |

复现前确认实际发布协议及线上 MediaMTX 版本，列出该版本确实可取得的字段。本地配置指向既有 WHIP 和 WHEP 路线，但不据此假定线上部署相同；若缺少会话级丢包、帧率等指标，使用现有 OBS 日志、云端计数和浏览器统计交叉判断，并明确不能区分的环节。不得为补齐指标另开端口、增加采集进程或上传敏感原始日志。

先在当前 1080p30、6000 Kbps、H.264 硬件编码设置下复现，至少两位观众同时观察持续运动画面。当前已经关闭 B 帧与人工直播延迟，不把它们列为默认待修改项。High Profile 不凭名称判错，核对实际协商与解码情况。

如实际源帧率已经不足，记录 OBS 编码瓶颈，再由用户确认后做单变量源端参数比较；不在服务器补帧或转码。若源正常、云端明显丢包或节流，则先定位现有链路或配置问题；不得以本计划为由新增中继、扩容或拆进程。需要范围外操作时单独提出，不假装播放器改动可以解决全部网络限制。

OBS 官方也区分编码性能与观众缓冲问题，正常本地预览不能独立证明分发链路健康。[编码性能](https://obsproject.com/kb/encoding-performance-troubleshooting)、[观众缓冲](https://obsproject.com/kb/stream-buffering-troubleshooting)

### 现有直播播放器的最小修复

- 只保留一个有效 Reader、PeerConnection 和当前音视频轨道集合。切流、离房、重连时清理定时器、帧回调、旧会话和轨道；旧异步结果不得覆盖新连接。
- 只有一个恢复控制者。页面负责获取有效凭据和有限退避；Reader 不再与页面同时无限重试。鉴权失败与真实关房不能无限恢复。
- `play()` 自动播放被阻止时走用户点击恢复，不把它误当作网络断开、重复建连。
- 只在前台、用户已启用节目、曾有正常画面且持续收到视频数据时检测冻结。建议 3 秒无新呈现帧触发一次恢复，每 60 秒最多两次，额度跨重连保留；低帧率本身不触发重连风暴，后台不误判。该阈值是兜底，不能用它放宽冻结验收。
- 先恢复浏览器自适应抖动缓冲，不强制压到零；现有固定 100ms 设置需做前后比较，不能把它当作端到端 100ms 的保证。
- 每秒最多一次、不重叠地采样统计。使用计数差分测最近窗口，连接更换、SSRC 变化、计数归零或采样断档时重置基线。缺失值为未知，真实 0fps 为异常，24fps 来源不能按 30fps 阈值误判。
- 缓冲指标用 `ΔjitterBufferDelay / ΔjitterBufferEmittedCount`；按实际发布会话 ID 读取源指标，多观众共享短时采样结果，不能把同路径多个会话混为一个。[WebRTC 统计规范](https://www.w3.org/TR/webrtc-stats/)、[当前仓库使用版本的指标源码](https://raw.githubusercontent.com/bluenviron/mediamtx/v1.18.2/internal/metrics/metrics.go)

浏览器编码支持存在边界；本轮保留现有 H.264 和 Opus 推流路线，不引入 HLS、多码率或转码回退。[MediaMTX 浏览器编码限制](https://mediamtx.org/docs/features/webrtc-specific-features)

### 延迟测量

用源画面内的计时器和同镜头拍摄的接收屏幕测量端到端延迟。远程设备则使用经过校准的时钟并记录测量误差。分别统计首次出画、稳定播放、恢复后延迟；周期性取样观察是否随时间积累。

不把“连接成功”“解码帧率恢复”或“RTT 低”当成低延迟证据。0.5 秒保留为优化目标，不作为所有网络的承诺；若稳定但仍慢，报告实际分位数和原因，不通过频繁重连美化结果。

| 同设备对照         | iPad Safari 用来判断浏览器差异，不代替 iPad Edge 验收；桌面 WebKit 同样不能代替真机                                                                                                                                       |
| 直播统计测试       | 缺值、0fps、24fps、计数重置、迟到 Promise、并发轮询、发布者变更、后台和有限恢复全部覆盖                                                                                                                                   |
| 真实直播短测和长测 | 先两位观众 30 分钟，再 Host＋四位独立观众 60 分钟；使用持续运动源，源实际输出接近 30fps，不以假摄像头测试代替 OBS                                                                                                         |
| 流畅度目标         | 在源实际输出至少 29fps 的测试条件下，观众至少 95% 的 5 秒窗口呈现帧率不低于 27fps；前台稳态无超过 2 秒冻结，不出现反复超过 1 秒冻结；所有重连和卡顿计入报告                                                               |
| 直播延迟目标       | 稳定网络下以 P95 不高于 1 秒且不持续积累为阶段目标，并报告达到或偏离 0.5 秒优化目标的情况；不达标不得写成延迟问题已解决                                                                                                   |
| 不转码及既有功能   | FFmpeg 参数不出现音视频编码、混缩和重采样兜底；纯复制样本验证选中流内容；认证、踢人、关房、语音、节目切换、上传和缓存继续正常                                                                                             |

首播最初 10 秒可以单列启动阶段，真实后台时段单列移动端生命周期测试；恢复、冻结、重连时间不能从稳态样本中任意删去。统计 API 不可用时记为待人工验证，不填零，不自动通过。源端未达到约定帧率时先处理或报告源端问题，不能因此把整场低帧率判为通过。

统一计算口径如下：

- iPad 核心验收至少 20 个用例：向前和向后各 5 个、暂停跳转 4 个、连续三次快拖 3 个、后台返回 3 个；未缓存位置覆盖其中至少 4 个。连续快拖按最终目标验收，但保留每条命令结果。
- 同步偏差以同一呈现时刻的服务器权威播放锚点为基准，比较视频帧的媒体时间；不是只比较 Host 与观众的滑块值。分别报告播放和暂停场景，保留校时误差。
- 每位观众独立计算 5 秒窗口帧率、冻结次数、同步偏差和延迟 P95，不能合并观众数据掩盖单个设备异常。帧率以窗口内呈现计数增量除以真实单调时间计算，缺测窗口单列。
- 长测端到端延迟至少每 30 秒取样，所有冻结或重连后的首次恢复另取样；记录录像帧率、时钟校准误差和原始样本。采样不足不出具确定的 P95 结论。
- “稳定网络”在测试前登记，参考条件为 5 分钟基线中媒体连接 RTT P95 不超过 200ms、丢包率不超过 1%，并记录线路、连接协议和抖动。若统计缺失，则标为网络基线未确认；不满足条件的实际用户场景仍保留结果和未达标项，不在失败后重新定义或剔除。

## 实施批次与回退

1. 固定实际代码和线上发布基线，登记未完成草稿，建立原问题复现记录。只读核查当前活动房间、上传及 Worker 状态。
2. 完成“不转码”守卫、命令确认与定位控制，补齐单元和协议测试，再做 Mac 与 iPad 真机短测。
3. 完成直播统计与生命周期修复，按证据决定必要的现有代码调整，进行同条件前后对照。
4. 将新增前端测试纳入正式回归入口，完成类型、构建、协议、权限和既有业务回归。未覆盖的真机测试仍单列待验收。
5. 仅在无观众和无正在写入任务的维护窗口发布前后端匹配版本。保留旧发布及配置；本专项不需要数据库迁移。
6. 完成实际 iPad Edge 和 OBS 长测后，才关闭对应问题。发生回归则回退应用和相关配置，不恢复旧数据库去覆盖新业务记录，也不删除影片。
