## 已复现的代码缺陷

1. 每个 rVFC 均可触发按瞬时误差写入 `playbackRate`，写入差值门槛仅 0.001。量化 `currentTime` 的纯内存仿真中，10 秒可触发 300 次写入。
2. `waiting` 没有锁存保护。`readyState=2`、前缓冲 0.2 秒、落后 2.5 秒时，发送 waiting 事件就能触发新的自动 seek。
3. 自动硬跳只有 5 秒冷却，没有跨 intent 预算。模拟每次 seek 首帧耗时 1.5 秒，25 秒内同 revision 可发生 5 次自动跳转。
4. playing seek 完成允许 2 秒残差，并不是「100ms 同步已实现」。各端在锚点生效后才启动定位，定位与解码耗时会形成残差；不能为追求数字而提前改变尚未生效的显式指令。

独立只读仿真：90 秒、准确累计 24fps 通知时基、30 秒前缓冲，仅第 5 秒一次 250ms 外部停顿。原控制器在调速写入无成本时最终偏差约 150ms；每次写入引起 200ms 解码推进暂停时，出现 56 次调速、最终落后约 1292ms。早期 `now + 1000/24` 调度在 10ms 步进下实际约 20fps，所得 52 次/1138ms 已由准确时基结果取代。它证明当前控制器会放大管线扰动，不证明实际 iOS 27 的每次写入一定停顿 200ms。

WebKit [Bug 163433](https://bugs.webkit.org/show_bug.cgi?id=163433) 有 iOS 调速导致音画短暂停顿的历史反馈，2024–2025 年仍有相关报告。这里只用作机制佐证，不能替代本次真机因果测量。当前影片原文件为 HEVC Main10 + AAC；RTT 接近既不能证明吞吐/解码正常，也不足以把规律性跳顿归因硬件。

## 修复约束与验证门禁

- 稳态纠偏与逐帧观测分离：低频采样、离散档位、滞回和保持时间，避免逐帧改速及恢复原速后立即重新进入。
- waiting、帧无进展和低缓冲期间不追赶；自身调速引发的短等待不能立即反向改速制造第二次停顿。
- 自动硬定位须持续超差、健康缓冲和帧进展，并有跨 intent 预算与退避；明确 Host 拖动仍保留原权威时序和实际目标帧验证。
- SYNC 保留真实值，明确「播放中」不等于「同步成功」，展示当前模式、调速/定位操作计数与前缓冲。诊断写入限频，不增加逐帧同步存储负担。
- 补充确定性管线副作用、分档时钟、waiting/恢复、自动跳转预算测试；再跑原三浏览器鉴权/拖动/暂停/恢复用例。
- 新增移动视口 WebKit 连续 35 秒真实帧采样：全段偏差分布、最大帧间隔、ratechange、seeking、waiting、stalled、pause，而非单次瞬时达标。模拟器仍不等于真实 iOS，也不能通过 muted=false 断言音频连续。

## 已落地的修复

- `vod-controller.ts`：500ms 独立纠偏采样、离散 ±5% 档位；进入 450ms / 退出 50ms 滞回、至少 2 秒保持。滞回包含返回 1× 时的人工管线恢复成本，防止立刻重复追赶。SYNC 仍显示原始真实误差，未截断/减偏。
- `waiting`、帧不推进、低缓冲保护；短暂的调速自发 waiting 不立即反向改速；稳定帧推进、readyState ≥3、足够前缓冲之后才重启纠偏。完全缓存片尾不误报缓冲。
- 大漂移自动定位必须持续超差、健康缓冲、持续呈现，每 120 秒最多一次，另保留冷却；明确 Host 指令、未来锚点及同目标重复拖动不受自动预算抑制。
- `RoomPage` 先将 waiting 交给控制器，再接受同 revision 快照，堵住恢复保护生效前先 tick 的集成窗口。原生对照在帧回调、周期控制、可见性事件三处隔离。
- 新 `vod-diagnostics.ts`：明确模式/误差说明，诊断和 trace 各最多 1Hz 持久化。记录真实速度/定位写入与操作原因、前缓冲、帧龄、readyState，不采集或外传凭据。
- 保留已保护的媒体地址、鉴权、Range、账户、服务端锚点与数据库结构，不改变 OBS/直播路径。

新增闭环单测使用另一组条件：1.46 秒初始定位残差、30fps、100ms `currentTime` 分档、每次改速触发 waiting 与人工解码暂停。新旧控制器在相同输入下比较：

| 场景                     | 旧版改速次数 / 最终漂移 | 新版改速次数 / 最终漂移 |
| ------------------------ | ----------------------- | ----------------------- |
| 初始落后，200ms 改速成本 | 75 / 1000ms             | 2 / 200ms               |
| 初始落后，300ms 改速成本 | 51 / 1300ms             | 2 / 300ms               |
| 初始超前，200ms 改速成本 | 27 / 0ms                | 2 / 200ms               |
| 初始超前，300ms 改速成本 | 103 / 1000ms            | 2 / 300ms               |

新版均无自动 seek，最后 30 秒无进一步速度写入，最终恢复 1×；不把旧版某个末帧误差恰为 0 当作连续稳定。控制器共 63 项单测通过，新增回归曾先在旧实现出现预期失败。这里的成本与时基是模拟参数，不是 iOS 实测。

已知残余：保持原指令生效顺序，不做提前 future seek。若某设备一次定位确实消耗 1.5 秒，随后会有可见的追赶阶段；上述 300ms 成本组 ±5% 约 39.3 秒回 1×，不是立即达到 Mac 109ms 的保证。没有通过提前执行 Host 指令或宽报「同步成功」掩盖这一点。
